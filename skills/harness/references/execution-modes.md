# 실행 모드 상세 안내 — Orca 조율 계층과 워커 내부 실행 모드

이 문서는 하네스 v2의 조율 계층(Orca 워커 협업)과 워커 내부 실행 모드의 주요 기능, 제약 사항, 선택 기준을 설명한다. `SKILL.md`의 2-1단계를 보충하는 문서다.

하네스는 두 계층으로 실행한다. 조율 계층은 항상 Orca이고, 워커 내부 실행 모드는 Task마다 고른다.

```
[코디네이터] ── Orca Run / Task DAG ──┬→ [Orca 워커: claude] → 워크플로 조율 | 서브에이전트 위임 | 직접 수행
   (오케스트레이터 스킬을 불러온 세션)   └→ [Orca 워커: codex]  → 직접 수행
```

## 1. 조율 계층: Orca 워커 협업

오케스트레이터 스킬을 불러온 세션이 Orca **코디네이터**가 된다. 코디네이터는 `orchestration` 스킬로 Run과 Task DAG를 만들고, Task마다 Orca **워커**(별도의 Claude 또는 Codex 세션)를 시작해 결과를 돌려받는다. 워크트리와 터미널을 다뤄야 하면 `orca-cli` 스킬을 쓴다.

명령의 정확한 플래그와 복구 절차는 `orchestration` 스킬이 실행 중인 Orca 버전에 맞춰 제공한다(`ORCA skills get orchestration`). `ORCA`는 그 스킬이 정한 실행 파일을 가리키는 자리 표시자다. 이 문서와 오케스트레이터에는 명령 세부 사항을 옮겨 적지 않고, 아래 흐름만 설계 기준으로 삼는다.

```
[코디네이터]
    ├── ORCA orchestration run-create --objective "..."            ← Run 생성
    ├── ORCA orchestration task-create --spec-file ... --deps '[...]'   ← Task DAG 등록
    ├── ORCA orchestration worker-start --task <id> --agent claude|codex --worktree current
    ├── 턴 종료 → Orca가 깨움 → 깨운 메시지가 알려 준 check 실행
    │     ├── question    → reply
    │     ├── worker_done → Task 정산 → task-list --ready의 Task 시작
    │     └── escalation  → send로 재지시, 재시도, 또는 사용자 보고
    ├── ORCA orchestration send --to dispatch:<id> ...             ← 맥락을 유지한 채 후속 지시
    └── 모든 Task 정산 → Task별 결과·증거·미해결 사항 보고
```

**주요 기능:**
- **Run** — 하나의 목표를 묶는 이름 공간이자 코디네이터의 수신함이다. Task DAG를 쓰려면 Run을 먼저 만든다.
- **Task와 의존 관계** — `task-create --deps`로 선행 Task를 지정한다. 선행 Task가 끝난 Task는 `task-list --ready`에 나타나며, 코디네이터는 깨어날 때마다 그 Task를 시작한다.
- **워커** — `worker-start --agent`로 워커 종류를 고른다. 워커는 독립된 세션이므로 Task spec에 필요한 맥락을 모두 넣는다. spec은 `--spec-file`로 넘기면 따옴표와 백틱을 이스케이프하지 않아도 된다.
- **메시지** — 코디네이터는 `send --to dispatch:<id>`로 워커에게 지시한다. 일하는 중인 워커는 바로 읽고, 끝났거나 닫힌 워커는 후속 Task로 받아 다시 `worker_done`으로 보고한다. 워커는 `ask`로 코디네이터에게 묻고 턴을 끝내며, 코디네이터는 `reply`로 답한다.
- **결정 게이트** — `gate-create --task`로 Task를 막아 두고 사용자 결정을 받은 뒤 `gate-resolve`로 푼다.
- **워크스페이스 배치** — `--worktree current`는 코디네이터의 워크스페이스를 함께 쓴다. `new-child`는 워커 전용 워크트리를 만든다.

**특징:**
- 워커가 이전 대화와 작업 내역을 기억하므로 "앞서 만든 초안의 2절만 고쳐 줘"와 같은 후속 지시를 `send`로 처리할 수 있다.
- 역할마다 Claude와 Codex를 골라 쓸 수 있다. 만든 에이전트와 다른 종류의 에이전트가 검토하면 같은 모델이 놓치는 오류를 잡을 수 있다.
- 워커는 Orca에 채팅이나 터미널로 나타나므로 사용자가 진행을 지켜보고 필요하면 직접 대화할 수 있다.
- 코디네이터가 기다리는 동안 토큰을 쓰지 않는다. 워커를 시작하고 턴을 끝내면 Orca가 깨운다.

**제약 사항:**
- 코디네이터는 폴링하거나 감시 스크립트를 돌리지 않는다. 스크립트가 `check`를 실행하면 코디네이터가 받아야 할 메시지를 가져가 버려 Orca가 코디네이터를 깨울 수 없다.
- 워커의 터미널에 직접 입력해 조종하지 않는다. 지시는 `send`로 보낸다.
- 워커의 워크스페이스를 직접 체크아웃하지 않는다. `worker-start`가 만들게 한다.
- 같은 파일을 동시에 고치는 워커는 워크스페이스를 나눠야 한다. 나눈 워커는 상대 경로의 `_workspace/`가 코디네이터의 것과 다르므로 spec에 절대 경로를 적고, 코드 변경은 워커의 브랜치에 남겨 코디네이터가 병합한다.
- 워커끼리는 직접 대화하지 않는다. 코디네이터가 한 워커의 결과를 다른 워커에게 `send`나 다음 Task의 spec으로 전달한다.
- 워커가 조용하거나 응답이 늦다는 것만으로는 종료됐다고 볼 수 없다. 그 이유만으로 워커를 중지·포기·재시작하지 않는다. Orca가 Task의 재시도를 막으면 막힌 Task를 새 Run이나 새 Task로 우회하지 않는다.
- Orca 워커는 서브에이전트보다 무겁다. 워커 수는 3~5명이 적당하며, 항목 수만큼 워커를 늘리지 않는다.
- 에이전트 정의 프론트매터의 `tools`와 `model`은 Orca 워커에 적용되지 않는다. 수정 가능 범위는 spec에, 모델은 `worker-start --model`에 적는다.

**Orca Task로 나눌 기준:** 다음 가운데 하나에 해당할 때만 별도 Task로 나눈다. 해당하지 않으면 한 워커 안에서 워크플로나 서브에이전트로 처리한다.

| 기준 | 예시 |
|------|------|
| 전문 역할이 다르고 결과를 다음 Task에 넘겨야 한다 | 분석가 → 설계자 → 구현자 |
| 같은 전문가에게 피드백을 돌려보내 고치게 해야 한다 | 작성자와 검토자가 초안을 주고받으며 수정 |
| 다른 에이전트가 필요하다 | Claude가 구현하고 Codex가 교차 검토 |
| 같은 파일을 동시에 고쳐 워크스페이스를 나눠야 한다 | 모듈별 병렬 마이그레이션 |
| 사용자가 워커를 지켜보거나 직접 대화해야 한다 | 사용자와 함께 다듬는 기획 워커(`--keep-open`) |

**Task spec에 넣을 내용:** 따를 에이전트 정의와 스킬의 경로, 대상과 입력 경로, 할 일, 수정 가능 범위, 산출물 경로, 완료를 증명할 증거, 워커 내부 실행 모드. 명령이 0이 아닌 값으로 끝났을 때 Task 실패로 볼지, 그 결과를 기록하는 것이 산출물인지도 적는다.

## 2. 워커 내부 모드 A: 워크플로 조율

Claude 워커가 `Workflow` 도구로 조율 스크립트를 실행한다. 분산 실행(팬아웃), 반복, 조건 분기와 같은 제어 흐름을 모델이 그때그때 판단하지 않고 **코드**가 정한다. 따라서 같은 입력을 주면 같은 구조로 재현하기 쉽고, 많은 에이전트를 병렬로 실행하기에도 알맞다.

```
[Claude 워커] → Workflow(script)
           ├── phase('탐색'): pipeline(items, item => agent(...))
           ├── phase('검증'): 발견한 항목마다 반박할 근거를 찾아 검증(병렬)
           └── return { confirmed }   ← 구조화된 최종 결과
```

**주요 기능:**
- `agent(prompt, opts)` — 서브에이전트를 실행한다. `opts.schema`에 JSON 스키마(JSON Schema)를 지정하면 스키마 검증을 마친 구조화 객체를 반환한다. 별도로 파싱할 필요가 없으며, 스키마와 맞지 않으면 자동으로 다시 시도한다. `opts.agentType`을 지정하면 `.claude/agents/`에 정의된 사용자 정의 유형을 쓸 수 있다. `opts.effort`로 추론 강도를 조절하고, `opts.isolation: 'worktree'`로 파일 변경을 격리한다.
- `pipeline(items, stage1, stage2, ...)` — 각 항목이 여러 단계를 독립적으로 거친다. 단계 사이에 동기화 장벽이 없으므로 **다단계 작업에서는 기본으로 사용한다.**
- `parallel(thunks)` — 모든 작업이 끝날 때까지 기다리는 동기화 장벽이다. 다음 단계에서 이전 단계의 결과 **전체**가 필요할 때만 쓴다. 중복 제거 또는 전체 개수를 기준으로 한 조기 종료가 이에 해당한다.
- `phase(title)` / `log(msg)` — 진행 상황을 묶어서 표시하고 사용자에게 현재 작업을 알린다.
- `budget` — 사용자가 지정한 토큰 예산(예: "+500k")과 연동한다. `budget.total`과 `budget.remaining()`을 이용해 작업 규모를 동적으로 조절한다.
- `workflow(nameOrRef, args)` — 다른 워크플로를 한 단계까지 중첩해 실행한다. 작업을 계층적으로 위임할 때 쓴다.

**특징:**
- 코드가 제어 흐름을 정하므로 같은 입력이면 같은 실행 구조를 따른다.
- 구조화 출력(`schema`)을 사용하므로 단계 사이에 스키마에 맞는 데이터를 전달할 수 있다.
- `resumeFromRunId`로 중단한 실행을 이어 갈 수 있다. 바뀌지 않은 `agent()` 호출은 캐시된 결과를 즉시 반환하므로 일부만 다시 실행할 때 드는 비용이 적다.
- 백그라운드에서 실행하며, 작업이 끝나면 알림을 보낸다.

**제약 사항:**
- **사용자가 먼저 요청해야 한다.** 사용자가 워크플로나 여러 에이전트의 조율을 직접 요청했거나, `Workflow` 호출을 명시한 스킬을 실행한 경우에만 쓸 수 있다. 워커에게는 Task spec이 사용자 요청이므로, 코디네이터는 spec에 `Workflow` 도구로 실행하라고 명시한다. 다만 기본 에이전트 수는 적게 잡고, 대규모 분산 실행은 사용자가 명시적으로 요청했을 때만 사용한다.
- `Workflow`는 Claude Code 도구다. Codex 워커의 Task에는 쓸 수 없다.
- 스크립트에는 순수 JavaScript만 쓸 수 있으며 TypeScript 문법은 쓸 수 없다. `Date.now()`, `Math.random()`, 인자 없는 `new Date()`는 실행 재개를 방해하므로 사용할 수 없다. 타임스탬프는 `args`로 전달한다.
- `meta` 블록에는 리터럴만 쓸 수 있다. 변수, 함수 호출, 스프레드 문법은 허용되지 않는다.
- 세션마다 동시에 실행할 수 있는 에이전트 수에 상한이 있다. 상한을 넘은 작업은 자동으로 대기열에 들어간다. 한 워크플로가 실행되는 동안 호출할 수 있는 전체 에이전트 수도 제한해 과도한 실행을 막는다.
- 실패했거나 건너뛴 `agent()`는 `null`을 반환한다. `parallel()`은 호출이 실패해도 예외를 던지지 않으므로 결과에 반드시 `.filter(Boolean)`을 적용한다.
- `parallel()` 장벽은 작업이 끝나는 시점을 맞출 뿐 끝난 뒤의 수정은 막지 않는다. 워크플로 Task가 끝난 뒤 코디네이터가 `send`로 다시 깨운 워커가 그 산출물 파일을 고칠 수 있으므로, 다음 Task로 넘기는 경계에서 산출물을 동결한다(`orchestrator-template.md`의 4단계).

**잘 맞는 작업:** 파일 N개 또는 관점 M개처럼 목록을 미리 정할 수 있는 분산 실행, 새 항목이 없을 때까지 반복하는 방식(Loop-until-dry)과 적대적 검증, 대규모 전환·감사, 구조화된 보고서 생성

**맞지 않는 작업:** 대화를 이어 가며 작업 대상을 찾아야 해서 목록을 미리 정할 수 없는 일, 중간에 사용자와 자주 상의해야 하는 일

> 구체적인 스크립트 기본 틀과 주의할 점은 `workflow-recipes.md`를 참고한다.

## 3. 워커 내부 모드 B: 서브에이전트 위임

Claude 워커가 `Agent` 도구를 한 번만 호출해 서브에이전트에 맡기는 방식이다. 결과만 워커에 돌아오며 에이전트끼리 통신하지 않는다.

```
[Claude 워커] → Agent(서브A) ─┐
              → Agent(서브B) ─┼→ (병렬, 기본값은 백그라운드 실행) → 완료 알림을 받음 → 결과를 모음
              → Agent(서브C) ─┘
```

**특징:**
- 실행 부담이 적고 빠르다. 워커는 요약된 결과를 받는다.
- 서로 독립적인 호출을 **한 메시지에 묶어** 보내면 동시에 실행된다.
- 기본적으로 백그라운드에서 실행한다. 결과를 곧바로 받아야 한다면 `run_in_background: false`를 지정한다.
- 워커는 이미 위임한 검색을 다시 수행하지 않고 결과를 기다린다.

**제약 사항:**
- 에이전트끼리 통신할 수 없고, 호출이 끝나면 대화 맥락도 이어지지 않는다. 맥락을 유지한 채 다시 지시해야 하는 전문가는 서브에이전트가 아니라 Orca 워커로 둔다.
- 서브에이전트의 결과는 워커가 모아 파일로 남기고 `worker_done`으로 보고한다.
- `Agent`는 Claude Code 도구다. Codex 워커의 Task에는 쓸 수 없다.

**잘 맞는 작업:** 한 번으로 끝나는 조사·수집, 필요한 전문가를 골라 결과만 받는 작업, 한 차례의 독립 검증

**맞지 않는 작업:** 결과를 주고받으며 반복해서 수정해야 하는 일, 실행 흐름을 미리 정할 수 있는 대규모 분산 작업

**직접 수행:** 나눌 필요가 없는 Task는 워커가 스스로 처리한다. Codex 워커의 Task는 모두 이 방식으로 쓴다.

## 4. 실행 모드를 고르는 결정 트리

먼저 작업을 Orca Task로 나누고(1절의 「Orca Task로 나눌 기준」), 그다음 Task마다 워커 내부 실행 모드를 고른다.

```
이 작업은 별도 Orca 워커가 필요한가?
(다른 전문 역할 / 피드백을 돌려보낼 전문가 / 다른 에이전트 / 워크스페이스 분리 / 사용자가 지켜봄)
├── 예 → 별도 Task로 등록하고 워커 종류(claude 또는 codex)를 고른다.
└── 아니요 → 기존 Task 안에서 처리한다.

Task마다: 작업 목록·검증 기준·반복 조건을 미리 코드로 표현할 수 있는가?
├── 예 → 워크플로 조율(모드 A, Claude 워커)
│        제어 흐름을 모델이 판단하지 않고 코드로 정한다.
│        spec에 Workflow 도구로 실행하라고 명시하고 에이전트 수를 필요 이상으로 늘리지 않는다.
│
└── 아니요 → 결과만 받으면 되는 독립 작업으로 나눌 수 있는가?
              ├── 예 → 서브에이전트 위임(모드 B, Claude 워커)
              └── 아니요 → 직접 수행
```

**자주 쓰는 조합:**

| 조합 | 구성 | 예시 |
|------|------|------|
| 워크플로 수집 → 워커 협업 통합 | Task 1(모드 A) → Task 2·3(작성자와 검토자 워커) | 자료를 대량으로 나누어 수집한 뒤, 서로 맞지 않는 데이터를 작성자와 검토자가 주고받으며 정리 |
| 워커 생성 → 워크플로 검증 | Task 1(직접 수행) → Task 2(모드 A) | 워커가 초안을 만든 뒤, 발견한 항목마다 적대적 검증을 분산 실행 |
| Claude 구현 → Codex 교차 검토 | Task 1(claude) → Task 2(codex, 직접 수행) | 구현 결과를 다른 에이전트가 검토하고, 지적 사항을 코디네이터가 `send`로 구현 워커에 돌려보냄 |
| 사전 조사 → 워크플로 본 작업 | 코디네이터 또는 Task 1 → Task 2(모드 A) | 작업 목록을 먼저 파악한 뒤, 그 목록을 spec에 넣어 워크플로의 `args`로 전달 |

**조율 전에 목록을 확인하는 원칙:** 워크플로를 시작하기 전에 파일 목록, 검토 대상, 조사 항목을 간단히 살펴보고 작업 목록을 확정한다. 실행 전에 작업 형태를 파악하면 스크립트가 단순해지고 불필요한 작업이 줄어든다.

## 5. 이전 방식에서 전환

### 5-1. v1에서 전환

기존 v1 하네스가 만든 조율 스킬이나 에이전트 정의를 발견하면 아래 표에 따라 바꾸도록 제안한다.

| v1 요소 | 상태 | 대체 |
|---------|------|---------|
| `TeamCreate(team_name, members)` | **제거됨** | Orca Run을 만들고 역할마다 `worker-start`로 워커를 시작한다. 팀 객체를 따로 만들 필요가 없다. |
| `TeamDelete` / "팀 정리" 단계 | **제거됨** | 해당 단계를 삭제한다. 워커는 완료를 보고한 뒤 스스로 닫힌다. |
| "세션당 한 팀만 활성화" 제약 | **형태 변경** | 명시적인 팀 객체가 없어졌으므로 v1의 제약은 적용되지 않는다. 워커는 Run 단위로 묶인다. |
| `SendMessage({to: "all"})` 전체 전송 | 변경 | 필요한 워커에게만 `send --to dispatch:<id>`를 각각 보낸다. |
| `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1` | **불필요** | 문서와 스크립트에서 모두 제거한다. |
| `model: "opus"`를 모든 에이전트에 강제 | 정책 폐기 | 업무 특성에 따라 모델을 각각 고른다. 판단이 애매하면 `sonnet`을 쓰고, 모델 상속은 의도적으로 선택한 경우에만 남긴다. |
| 대규모 분산 실행을 팀으로 구성 | 개선 | 워커 한 명의 `Workflow` 스크립트로 옮긴다. 코드로 제어 흐름을 정하고, 구조화 출력을 사용하며, 실행을 재개할 수 있다. |
| 조율 스킬의 "0단계: 대화 맥락 확인" | 유지 | 기존 절차를 유지하되 Orca Run ID·Dispatch ID 기록과 워크플로의 `resumeFromRunId` 옵션을 추가한다. |
| `_workspace/` 파일 작성 규칙 | 유지 | 그대로 사용한다. |
| `CLAUDE.md` 위치 안내와 변경 이력 | 유지 | 그대로 사용하고 실행 환경(Orca) 한 줄을 추가한다. |

### 5-2. 세션 내부 조율에서 Orca 조율로 전환

Orca 조율을 도입하기 전의 v2 하네스는 한 세션 안에서 `Agent(name:)`, `SendMessage`, `TaskCreate`로 조율했다. 이런 조율 스킬을 발견하면 아래 표에 따라 바꾸도록 제안한다.

| 이전 요소 | 대체 |
|-----------|------|
| 메인 에이전트(리더) | Orca 코디네이터(오케스트레이터 스킬을 불러온 세션) |
| `Agent(name: ...)`로 실행한 지속형 에이전트 | `worker-start --task <id> --agent claude\|codex`로 시작한 Orca 워커 |
| `SendMessage({to: name})` | `send --to dispatch:<id>` |
| 팀원이 리더에게 보내는 질문 | 워커의 `ask`, 코디네이터의 `reply` |
| `TaskCreate` / `TaskUpdate` / `TaskList`와 `depends_on` | `task-create --deps` / `task-update` / `task-list` |
| `TaskStop` | `orchestration` 스킬의 복구 참조 문서가 정한 중지 절차 |
| 오케스트레이터가 직접 호출하던 `Workflow`와 단발 `Agent` | 해당 Task를 맡은 Claude 워커의 내부 실행 모드로 옮기고 spec에 적는다. |
| 에이전트 정의의 `tools` 제한에 의존한 읽기 전용 역할 | 서브에이전트로 쓸 때만 유효하다. Orca 워커로 쓰면 spec에 수정 금지를 명시한다. |

**전환 절차:**
1. 기존 조율 스킬에서 `TeamCreate`, `TeamDelete`, 전체 전송, 실험 플래그 참조를 제거한다.
2. 협업 구간을 Orca Task로 다시 나눈다(1절의 「Orca Task로 나눌 기준」). Task마다 워커 종류를 정하고 spec을 쓴다.
3. 분산 실행과 검증 반복 구간을 찾는다. 실행 흐름을 코드로 미리 정할 수 있다면 해당 Task의 워커 내부 실행 모드를 워크플로 조율로 정한다.
4. 조율에 쓰던 `Agent(name:)`, `SendMessage`, `TaskCreate`, `TaskUpdate`를 위 표에 따라 바꾼다.
5. 에이전트 정의에서 `model: "opus"` 일괄 지정을 제거하고, 근거가 있는 지정만 남긴다. `## 통신 규칙`을 `ask`와 `worker_done` 기준으로 고친다.
6. 6단계 검증(구조 검증과 시험 실행)을 다시 수행하고 `CLAUDE.md` 변경 이력에 기록한다.
