# 오케스트레이터 스킬 템플릿(v2)

오케스트레이터는 팀 전체를 조율한다. 오케스트레이터 스킬을 불러온 세션은 Orca 코디네이터가 되어 `orchestration` 스킬로 워커를 조율한다. 이 문서는 다음을 제공한다.

- **오케스트레이터 템플릿** — Orca Run, Task DAG, 워커 시작, 깨어났을 때의 처리, 산출물 동결, 통합
- **Task spec 템플릿** — 워커 한 명이 그것만 읽고 일할 수 있는 작업 지시서
- **워커 내부 실행 모드별 spec 작성법** — 워크플로 조율, 서브에이전트 위임, 직접 수행

모든 오케스트레이터는 0단계에서 기존 작업 내용을 확인한다. `_workspace/` 파일 구성 규칙, 오류 처리 방법, 테스트 시나리오도 반드시 포함한다.

오케스트레이터에는 이 하네스의 흐름에 필요한 Orca 명령의 뼈대만 적는다(아래 템플릿 수준). 그 밖의 플래그와 복구 절차는 옮겨 적지 않는다. `orchestration` 스킬이 실행 중인 Orca 버전에 맞는 가이드를 제공하며, 옮겨 적은 사본은 Orca가 갱신되면 어긋난다. 아래 템플릿의 `ORCA`는 `orchestration` 스킬이 정한 실행 파일을 가리키는 자리 표시자다.

## 오케스트레이터 템플릿

```markdown
---
name: {domain}-orchestrator
description: "{도메인} 에이전트의 협업을 조율한다. 사용자가 {초기 실행 키워드} 중 하나로 요청하면 사용하며, {도메인} 결과 수정, 부분 재실행, 업데이트, 보완, 다시 실행, 이전 결과 개선 같은 후속 작업에도 사용한다."
---

# {Domain} 오케스트레이터

## 실행 환경: Orca 워커 협업

이 스킬을 불러온 세션은 Orca 코디네이터다. 먼저 `orchestration` 스킬을 불러와
`ORCA skills get orchestration`으로 가이드를 읽는다. 실행 파일을 실행할 수 없으면 오류를 그대로
사용자에게 알리고 멈춘다. 워크트리나 터미널을 직접 다뤄야 하면 `orca-cli` 스킬을 쓴다.

- 워커를 시작한 뒤에는 턴을 끝낸다. Orca가 깨우기 전에는 폴링하거나 감시 스크립트를 돌리지 않는다.
- 워커에게 보내는 지시는 `send`로만 보낸다. 워커의 터미널에 직접 입력하지 않는다.
- 워커끼리는 직접 대화하지 않는다. 코디네이터가 결과를 다음 Task의 spec이나 `send`로 전달한다.
- 이 문서에 적힌 Orca 명령이 `orchestration` 가이드와 다르면 가이드를 따른다.

## 작업 절차

### 0단계: 기존 작업 확인(후속 요청 처리)

1. `_workspace/`가 있는지 확인한다.
   - 없으면 → 처음부터 실행
   - 있고 일부만 고쳐 달라는 요청이면 → 해당 Task만 다시 실행
   - 있고 새 입력을 받았으면 → 기존 `_workspace/`를 `_workspace_{ts}/`로 옮기고 새로 실행
2. 일부만 다시 실행한다면 `_workspace/run_meta.json`에서 Run ID와 해당 Task의 Dispatch ID를 찾는다.
   - `ORCA orchestration run-current`로 이 세션에 그 Run이 묶여 있는지 확인한다. 묶여 있지 않으면
     `ORCA orchestration run-use --id {run_id}`로 다시 묶는다. Run에 묶이지 않은 세션의 `send`는 거부되고,
     워커의 보고도 Run의 수신함으로 가기 때문이다.
   - `ORCA orchestration send --to dispatch:{dispatch_id} --subject "{주제}" --body "{고칠 범위}"`로 후속 지시를 보낸다.
     끝난 워커는 `send`를 후속 Task로 받아 이전 맥락을 유지한 채 작업하므로 고칠 범위만 좁혀 지시한다.
     후속 지시는 새 Task ID와 Dispatch ID로 접수되므로 `_workspace/run_meta.json`에 추가로 기록한다.
   - `send`가 거부되면 새 워커를 시작하고 이전 산출물 경로를 spec에 넣는다.
3. 새로 실행하면 Run ID와 Task별 Dispatch ID를 `_workspace/run_meta.json`에 기록한다.

### 1단계: 준비

1. 사용자 입력을 분석해 {무엇을 파악하는지}를 확인한다.
2. `_workspace/`를 만들고 입력을 `_workspace/00_input/`에 저장한다.
3. Task마다 spec 파일을 `_workspace/00_specs/{task}.md`에 쓴다(아래 「Task spec 템플릿」).
4. {워크플로로 처리할 Task가 있으면: 파일 목록 / 조사 축 / 검토 대상을 간단히 살펴 배열로 확정하고 해당 spec에 넣는다.}

### 2단계: Run 생성 및 Task 등록

1. `ORCA orchestration run-create --objective "{목표}"`
2. Task를 의존 관계와 함께 등록한다.
   - `ORCA orchestration task-create --spec-file _workspace/00_specs/T1.md --task-title "{T1 작업명}"`
   - `ORCA orchestration task-create --spec-file _workspace/00_specs/T2.md --task-title "{T2 작업명}" --deps '["{T1의 task_id}"]'`3. {사용자 승인이 필요한 Task가 있으면: `ORCA orchestration gate-create --task {task_id} --question "{질문}"`으로 막아 둔다.}

### 3단계: 워커 시작 및 조율

1. `ORCA orchestration task-list --ready --brief`에 나온 Task마다 워커를 시작한다.
   - `ORCA orchestration worker-start --task {task_id} --agent {claude|codex} --worktree current`
   - 에이전트 구성 표의 모델 등급은 사용자가 하네스 설계를 승인하며 확정한 값이다. Claude 워커에는 등급 이름(fable, opus, sonnet)을
     그대로 `--model`에 넣는다. 모델 이름은 시작 전에 검증되지 않으므로 표에 없는 이름을 지어내지 않는다. Codex 워커에는 사용자가 모델을 지정했을 때만 붙인다.
   - 사용자가 채팅을 계속 쓸 워커에는 `--keep-open`을 붙인다.
2. 시작 결과에 `next`가 있으면 그대로 따른다. Dispatch ID를 `_workspace/run_meta.json`에 기록하고 **턴을 끝낸다.**
3. Orca가 깨우면 깨운 메시지가 알려 준 `check` 명령을 실행하고, 받은 묶음을 모두 처리한 뒤 다음 `check`로 넘어간다.
   - `question`: Task나 사용자 지시에서 답이 나오면 `ORCA orchestration reply --id {message_id} --body "{답}"`으로 답한다.
     답이 나오지 않으면 사용자에게 먼저 묻는다.
   - `worker_done`: 산출물 파일과 완료 증거를 확인한다. 실패로 보고된 Task를 완료로 처리하지 않는다.
     다시 `task-list --ready`를 확인해 준비된 Task를 시작한다.
   - `escalation`(`stopReason` 포함): 워커가 완료 보고 없이 멈췄다. `send`로 다시 지시하거나, 재시도하거나, 사용자에게 알린다.
4. 검토 결과를 작성자에게 돌려보낼 때는 `ORCA orchestration send --to dispatch:{작성자 dispatch_id}`로 보낸다.
   작성자가 이전 맥락을 유지하므로 "초안의 2절만"처럼 범위를 좁혀 지시할 수 있다. 메시지에는 요약과 파일 경로만 담는다.
5. 할 일이 없으면 턴을 끝낸다.

### 4단계: 산출물 동결

끝난 워커도 `send`를 받으면 다시 열려 작업한다. 다음 Task가 읽고 있는 산출물을 후속 지시로 고치면, 다음 Task는 바뀌기 전 내용을 읽고 작업하게 된다. 다음 Task가 읽을 파일이 도중에 바뀌지 않도록 Task를 넘길 때마다 산출물을 동결한다.

1. 선행 Task가 모두 `worker_done`으로 정산됐는지 확인한다.
2. 산출물 해시를 기록한다. 예: `shasum _workspace/{phase}_* > _workspace/freeze_{phase}.sha` (`md5sum`을 써도 된다)
3. 다음 Task의 spec에 산출물 경로와 해시 파일 경로를 함께 넣는다.
4. 동결한 뒤 고칠 내용이 생기면 `send`에 "기존 파일을 고치지 말고 `{phase}_{role}_{artifact}_v2.md`처럼 새 버전 파일로 쓰라"고 적는다.

### 5단계: 통합

1. `ORCA orchestration task-list`로 모든 Task가 끝났는지 확인한다.
2. Read로 각 산출물을 읽고 {통합/검증 로직}을 적용한다.
3. 최종 산출물을 만들기 직전에 `shasum -c _workspace/freeze_{phase}.sha`처럼 해시를 다시 계산해 동결한 산출물이 바뀌지 않았는지 확인한다. 해시가 다르거나 새 버전 파일이 생겼으면 무엇이 바뀌었는지 확인하고, 바뀌기 전 내용을 읽은 Task를 다시 실행할지 정한다.
4. {워크스페이스를 나눈 워커가 있으면: 각 워커의 브랜치를 하나씩 병합한다. 충돌은 다음 브랜치를 합치기 전에 해결하고, 통합 테스트를 통과한 뒤에만 다음 변경을 적용한다.}
5. 최종 산출물을 `{output-path}/{filename}`에 만든다.

### 6단계: 마무리

1. 나중에 검증하고 작업 과정을 확인할 수 있도록 `_workspace/`를 남긴다.
2. 사용자에게 Task별로 결과, 증거, 미해결 사항을 요약해 보고한다. 제외되거나 누락된 항목이 있으면 반드시 밝힌다.
   워커를 정리하는 절차는 없다. 워커는 완료 보고 뒤 스스로 닫히고, 열어 두기로 한 워커는 사용자가 쓰도록 남긴다.

## 오류 처리

| 상황 | 대응 방법 |
|------|------|
| `worker-start` 실패 | 같은 명령을 다시 실행하지 않는다. 결과의 `failedStage`를 읽고 `orchestration` 스킬의 복구 참조 문서를 따른다. |
| 워커가 완료 보고 없이 멈춘 경우(`escalation`) | `send`로 다시 지시한다. 그래도 실패하면 `orchestration` 스킬의 복구 참조 문서를 읽고 그 절차대로 같은 Task를 다시 시도한다. |
| Orca가 Task의 재시도를 막은 경우 | 사용자에게 보고하고 멈춘다. 막힌 Task를 새 Run이나 새 Task로 우회하지 않는다. |
| 워커가 조용하거나 응답이 늦은 경우 | 그 이유만으로 워커를 중지·포기·재시작하지 않는다. 종료 여부는 `orchestration` 스킬의 복구 참조 문서가 정한 절차로 확인한다. |
| 워커가 `failed`로 보고한 경우 | 완료로 처리하지 않는다. 실패 원인과 부분 산출물을 확인한 뒤 다시 지시하거나 사용자에게 보고한다. |
| 중지 원인이 사용량 한도 소진, 인증 만료, 권한 거부인 경우 | 다시 시도해도 결과가 같으므로 다시 지시하거나 대체 워커를 시작하지 않는다. 부분 산출물을 직접 열어 실제로 어디까지 진행됐는지 확인하고, 누락 내용을 `_workspace/`에 파일로 기록한 뒤 사용자에게 보고한다. 사용량 한도라면 풀리는 시각도 함께 알린다. 코디네이터는 직접 확인한 사실만 대신 반영하고, 에이전트의 판단(예: 어떤 자료를 왜 제외했는지)은 추측해 채우지 않는다. |
| 절반이 넘는 Task가 실패한 경우 | 사용자에게 알리고 계속 진행할지 확인한다. |
| 워커 내부 워크플로의 개별 `agent()` 실패(`null` 반환) | 워커가 `.filter(Boolean)`으로 제외하고 제외한 항목 수를 `log()`로 기록한다. 완료 보고와 최종 보고서에도 누락된 항목을 밝힌다. |
| 결과가 비어 있는 경우 | 성공으로 잘못 판단하지 않는다. 산출물 파일과 워커의 출력을 직접 확인한다. |
| 데이터가 서로 충돌한 경우 | 삭제하지 않고 출처와 함께 나란히 적는다. |

## 테스트 시나리오

### 정상 흐름
1. 사용자가 {입력}을 제공하면 2단계에서 Task {M}건을 등록하고 3단계에서 준비된 Task의 워커를 시작한 뒤 턴을 끝낸다.
2. `worker_done`으로 깨어날 때마다 다음 Task를 시작하고, 검토 피드백을 {K}회 돌려보낸 뒤 4단계에서 산출물을 동결하고 5단계에서 통합한다.
3. 예상 결과: `{output-path}/{filename}`이 생성되고 `run_meta.json`에 Run ID와 Dispatch ID가 기록된다.

### 오류 흐름
1. 3단계에서 {role-2} 워커가 완료 보고 없이 멈춰 `escalation`을 받는다.
2. `send`로 다시 지시한다. 그래도 실패하면 복구 참조 문서의 절차로 같은 Task를 다시 시도하고 기존 산출물 경로를 전달한다.
3. 최종 보고서에 "{role-2} 영역 일부 재작업"이라고 적는다.
```

## Task spec 템플릿

워커는 코디네이터의 대화를 보지 못한다. spec은 그것만 읽고 일할 수 있게 쓴다.

```markdown
# {Task 작업명}

역할: `.claude/agents/{role}.md`를 읽고 그 역할로 작업하라.
스킬: `.claude/skills/{skill}/SKILL.md`를 읽고 따르라.

## 대상과 입력
- {대상 파일·디렉터리, 선행 Task의 산출물 경로, 동결 해시 파일 경로}

## 할 일
- {구체적인 작업}

## 수정 가능 범위
- {고쳐도 되는 파일·디렉터리. 읽기 전용 역할이면 "어떤 파일도 고치지 않는다. 산출물 파일만 새로 쓴다."}

- `_workspace/{phase}_{role}_{artifact}.md` ({형식})

## 완료 증거
- {완료를 증명할 근거. 예: 테스트 명령과 통과 출력, 산출물의 필수 항목}
- {명령이 0이 아닌 값으로 끝나면 Task 실패인지, 그 결과를 기록하는 것이 산출물인지}

## 통신
- 스스로 정할 수 없는 사항은 추측하지 말고 코디네이터에게 `ask`로 묻고 턴을 끝낸다.
- 끝나면 산출물 경로와 완료 증거를 담아 `worker_done`으로 보고한다.
```

- 워크스페이스를 나눈 워커(`new-child`)의 spec에는 `_workspace/` 경로를 코디네이터 워크스페이스 기준의 **절대 경로**로 적는다.
- 새 워크트리에는 커밋된 파일만 있다. `.claude/agents/`와 `.claude/skills/`를 커밋하지 않았다면 역할·스킬 경로도 절대 경로로 적는다. 이 경우 워커 내부에서 `subagent_type`으로 사용자 정의 유형을 부를 수 없다.
- Codex 워커는 `.claude/` 아래의 파일을 스스로 불러오지 않으므로 역할과 스킬 경로를 빠뜨리지 않는다.
- 에이전트 정의 프론트매터의 `tools` 제한은 Orca 워커에 걸리지 않는다. 읽기 전용 역할은 「수정 가능 범위」에 반드시 적는다.

## 워커 내부 실행 모드별 spec 작성법

### 워크플로 조율 (Claude 워커)

spec의 「워커 내부 실행 모드」에 다음을 적는다. `Workflow` 도구는 사용자가 요청해야 쓸 수 있고, 워커에게는 spec이 사용자 요청이므로 실행 지시를 명시한다.

```markdown
## 워커 내부 실행 모드
- Workflow 도구로 아래 스크립트를 실행하라. 사용자가 이 오케스트레이터를 불러와 워크플로 실행에 동의했다. 기본 에이전트 수는 {N}명으로 제한한다.
- `args`: { items: [{확정한 목록}], ws: "{_workspace 경로}" }
- `meta`: `name`은 '{domain}-run', `phases`는 [{수집}, {검증}, {종합}]
- 수집: pipeline(args.items, item => agent(..., {schema: COLLECT}))
- 검증: 찾은 항목마다 적대적 검증 → .filter(Boolean) → 검증을 통과한 항목만 다음 단계로 전달
- 종합: 구조화된 결과를 return
- 완료 알림을 받기 전에 결과를 미리 단정하지 않는다.
- 반환값을 `_workspace/{phase}_{role}_result.json`에, 워크플로 `runId`를 `_workspace/{phase}_{role}_workflow_run.json`에 저장하라. `run_meta.json`은 코디네이터만 쓴다.
- 실패한 단계만 고쳐 다시 실행할 때는 `resumeFromRunId`로 재개하라.
```

스크립트가 길면 오케스트레이터 스킬의 `scripts/`에 파일로 두고 spec에 경로를 적는다. 자세한 예시는 harness 스킬의 `workflow-recipes.md`에서 확인한다.

### 서브에이전트 위임 (Claude 워커)

```markdown
## 워커 내부 실행 모드
- 한 메시지에서 Agent 도구를 아래 표대로 동시에 호출하라. `name`을 지정하지 않는 단발 호출이다.
- 완료 알림을 기다린다. 이미 맡긴 검색을 직접 다시 수행하지 않는다.
- 한 명이 실패하면 한 번 다시 시도한다. 다시 실패하면 누락 사실을 산출물과 완료 보고에 밝힌다.

| 서브에이전트 | `subagent_type` | 입력 | 산출물 |
|-------------|--------------|------|------|
| {agent-1} | {타입} | {소스} | `_workspace/{phase}_{agent}_{artifact}.md` |
| {agent-2} | {타입} | {소스} | `_workspace/{phase}_{agent}_{artifact}.md` |
```

`{타입}`에는 사용자 정의 유형의 이름이나 기본 제공 유형을 적는다.

### 직접 수행 (Claude 워커, Codex 워커)

```markdown
## 워커 내부 실행 모드
- 이 Task를 직접 수행하라.
```

Codex 워커의 Task는 모두 이 모드로 쓴다.

---

## Task 사이의 전달 규칙

- 워크플로 Task → 다음 Task: 워크플로가 반환한 구조화 데이터를 워커가 `_workspace/`에 저장하고, 다음 Task의 spec에 파일 경로를 적는다.
- 워커 협업 Task → 워크플로 Task: 산출물을 동결한 뒤(4단계) 파일 경로 목록을 워크플로 Task의 spec `args`에 넣는다.
- Task가 넘어가는 지점마다 데이터 전달 경로를 적어, 이전 Task의 결과를 찾지 못하는 일이 없게 한다.

---

## 작성 원칙

1. **문서 맨 위에 실행 환경을 밝힌다.** `orchestration` 스킬을 먼저 불러온다는 것과 코디네이터의 금지 사항(폴링, 터미널 직접 조종)을 적는다.
2. **에이전트 구성 표에 Task마다 워커 종류, 모델, 워커 내부 실행 모드를 적는다.** 선택 이유도 남긴다.
3. **Task spec은 그것만 읽고 일할 수 있게 쓴다.** 역할·스킬 경로, 수정 가능 범위, 산출물 경로, 완료 증거를 빠짐없이 적는다.
4. **워크플로 Task에서는 스크립트 구조를 자세히 적는다.** `phases`, `schema` 요약, `args`에 넣을 항목을 빠짐없이 명시한다.
5. **서브에이전트 Task에서는 Agent 매개변수를 빠짐없이 적는다.** `subagent_type`, `prompt`, 출력 경로를 명시한다.
6. **파일 경로를 분명히 적는다.** `_workspace/`를 기준으로 경로를 쓰고, 파일 이름은 `{phase}_{agent}_{artifact}.{ext}` 규칙을 따른다.
7. **Task 사이의 의존 관계를 밝힌다.** `--deps`와 산출물 경로가 서로 맞아야 한다.
8. **실제로 일어날 수 있는 오류에 대비한다.** 모든 작업이 성공한다고 가정하지 말고 상황별 처리 방법을 정한다.
9. **테스트 시나리오를 반드시 넣는다.** 정상 시나리오 한 가지와 오류 시나리오 한 가지 이상을 작성한다.
10. **이전 방식의 항목을 넣지 않는다.** TeamCreate, TeamDelete, `team_name`, 전체 전송, 실험 플래그, 조율용 `Agent(name:)`·SendMessage·TaskCreate를 참조했다면 잘못 작성한 것이다.
11. **Orca 명령의 세부 사항을 옮겨 적지 않는다.** 이 하네스에 필요한 명령의 뼈대만 적고, 플래그와 복구 절차는 `orchestration` 스킬의 가이드를 따르게 한다.

## `description`에 넣을 후속 요청 표현

첫 실행뿐 아니라 결과를 고치거나 다시 실행할 때도 이 스킬이 선택되도록 다음 표현을 넣는다.

- 재실행, 다시 실행, 업데이트, 수정, 보완
- "{도메인}의 {부분}만 다시"
- "이전 결과를 바탕으로", "결과 개선"
- 도메인에서 일상적으로 쓰는 요청 표현(예: 출시 전략 하네스라면 "런치", "홍보", "트렌딩")

후속 요청 표현이 없으면 첫 실행 뒤에는 이 하네스가 다시 선택되지 않을 수 있다.
